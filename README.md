# מחשבון תוספת תשלומים

**עמוד אחד שהמוכר פותח מול הלקוח.** מזינים סכום עסקה, בוחרים מספר תשלומים,
ומקבלים את התוספת ואת התשלום החודשי עם התוספת ובלעדיה.

אין שרת, אין בסיס נתונים, ואין תלות אחת. קובץ HTML יחיד שרץ בדפדפן.

## הכלל

מהמייל של החברה, 06.09.2026:

> להכפיל את סכום התשלום באחוז שמתאים למספר התשלומים המבוקש,
> ולעגל את התוצאה כלפי מעלה למספר עגול בעשרות שקלים.

```
תוספת = ceil( סכום × אחוז / 10 ) × 10
```

האחוזים: 21 ערכים, מ-4 תשלומים עד 24. מקור האמת הוא
[data/fee-table.json](data/fee-table.json).

```bash
node test.mjs              # 23,278 תנאים
node test.mjs --negative   # מוודא שהשער בכלל מודד
```

השער בודק שלושה דברים:

1. **מול הגיליון שהתקבל.** ‏126 תאים, המכפלה הגולמית והתוצאה המעוגלת.
2. **הפיצול מסתכם בדיוק.** אין אגורה שנעלמת בין התשלומים.
3. 🔴 **אין סחיפה.** הטבלה יושבת גם ב-`fee-table.json` וגם בתוך `index.html`.
   בלי השער הזה, עדכון אחוזים בקובץ אחד היה משאיר את השני מאחור **בשקט**,
   והמוכר היה קורא ללקוח מספר ישן.

## החלטות שנגזרו מהכלל, ולא מהמצאה

**חשבון שלמים בלבד.** הסכום מומר לאגורות והאחוז שמור כמאיות האחוז
(‏`2250` = 2.250%), ולכן שתי המכפלות שלמות.
‏`Math.ceil` על מכפלה בנקודה צפה שנופלת בדיוק על עשרת עלול לקפוץ עשרת שלמה
בגלל שארית של 1e-15, בלי שגיאה ובלי רמז. נמדד על 10.5 מיליון צירופים:
היום אין פער בין שתי השיטות, והשלמים מוציאים את השאלה מהתמונה.

**השארית בתשלום הראשון.** ‏4,160 ש"ח ב-12 תשלומים אינם 346.67 כפול 12.
הדף מציג `346.74` ואחריו 11 של `346.66`, כמקובל בחברות האשראי. יש שער
שמוודא שהסכימה חוזרת בדיוק לסך הכול.

**עד 3 תשלומים אין תוספת.** הטבלה מתחילה ב-4, ו-1 עד 3 אינם בה.
🔴 **הנחה שלנו, וטעונה אישור.** ראה [TASKS.md](TASKS.md).

**מעל 24 תשלומים הדף אינו נותן מספר.** אין נתון בטבלה, ולנחש אסור.
